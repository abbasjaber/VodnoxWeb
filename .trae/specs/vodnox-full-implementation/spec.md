# مواصفات تنفيذ VODNOX الكامل

## 1. المشكلة والأهداف

تحويل نموذج الواجهات HTML/JavaScript المرفق في `VODNOX-Full-Handoff/website/` إلى تطبيق Laravel حقيقي متكامل بقاعدة بيانات MySQL، مع الحفاظ على التصميم والهوية والوظائف المعتمدة.

### المستخدمون
- **super_admin**: مدير المنصة، يدير المؤسسات والاشتراكات والباقات والخوادم.
- **organization_admin**: مسؤول مؤسسة، يدير موظفيه وأقسامه واتصالاته وIVR وCRM وFORMS.
- **supervisor**: مشرف داخل المؤسسة.
- **agent**: موظف استقبال/اتصالات.
- **viewer**: قراءة فقط.
- **زائر عام**: يتصفح الموقع ويرسل استفسارات ويملأ نماذج عامة.

### الأهداف
- تطبيق Laravel 12 كامل يعمل من ملفاته الدائمة دون الاعتماد على مرفقات التنفيذ.
- عزل بيانات كل مؤسسة (Multi-tenancy) عبر `organization_id` مشتق من المستخدم المسجل.
- مصادقة كاملة بالأدوار والصلاحيات (Policies).
- وحدات الأعمال: الموقع العام، السوبر أدمن، مسؤول المؤسسة، الموظف، CRM، FORMS، إعدادات الاتصالات وIVR، المجيب الذكي (قريباً).
- واجهة مطابقة للتصميم المرفق بالعربية والإنجليزية RTL/LTR والوضعين الفاتح والمظلم.

### غير الأهداف (Non-goals)
- لا تشغيل فعلي لـ Asterisk/SIP/WebRTC في هذه المرحلة (محاكاة فقط).
- لا بناء AI للمجيب الذكي (صفحة "قريباً" فقط).
- لا بوابة دفع فعلية (تسجيل يدوي للمدفوعات فقط).
- لا رفع ملفات للنماذج.
- لا ربط تلقائي بين FORMS وCRM.
- لا تسجيل عام ذاتي للمستخدمين.

## 2. المتطلبات الوظيفية

### 2.1 الموقع العام
- صفحات: الرئيسية، الخدمات، الأسعار، من نحن، اتصل بنا، الدخول.
- مطابقة التصميم والرسومات SVG والحركات والمحتوى العربي والإنجليزي.
- نموذج اتصل بنا: حفظ الاستفسار في قاعدة البيانات؛ إرسال بريد فقط عند وجود SMTP صحيح.
- الأسعار قابلة للضبط من قِبل السوبر أدمن (لا أرقام مخترعة).

### 2.2 المصادقة والأدوار
- دخول بـ username/password، CSRF، rate limiting (5 محاولات/دقيقة لكل بريد+IP)، تجديد session بعد الدخول، إبطال session عند الخروج.
- أدوار: super_admin, organization_admin, supervisor, agent, viewer.
- الوجهة بعد الدخول حسب الدور.
- منع التسجيل العام.
- إنشاء السوبر أدمن الإنتاجي عبر أمر Artisan تفاعلي أو متغيرات بيئة (لا حساب افتراضي منشور).

### 2.3 عزل المؤسسات (Multi-tenancy)
- `organization_id` في كل الجداول التابعة للمؤسسة.
- اشتقاق المؤسسة من المستخدم المسجل؛ عدم الثقة في `organization_id` من الطلب.
- Policies على كل Show/Edit/Export/Download/API.
- منع IDOR بين مؤسستين (اختبار فعلي).

### 2.4 السوبر أدمن
- Overview، المؤسسات (CRUD + تفاصيل بتبويب: معلومات، اشتراك، مستخدمون، تحويلات وأرقام، IVR وطوابير، استخدام، تسجيلات، فواتير، نشاط).
- الاشتراكات، الباقات والحدود، الفواتير والمدفوعات (Decimal، لا يصبح paid تلقائياً عند رفع إثبات)، الاستخدام، خوادم الاتصالات، التكاملات، الفريق والصلاحيات، سجل النشاط، إعدادات المنصة.
- إدارة اشتراكات CRM وFORMS وSmart IVR للمؤسسات.

### 2.5 مسؤول المؤسسة
- Overview، الموظفون والأدوار والصلاحيات، الأقسام، التحويلات والأجهزة، طوابير الاتصال، IVR، الأرقام ومسارات الاتصال، سجل المكالمات، التسجيلات، تقارير الأداء، اشتراك المؤسسة والفواتير، إعدادات المؤسسة، سجل النشاط.
- لا يعرض بيانات سيرفر سرية أو صلاحيات سوبر أدمن.

### 2.6 الموظف والاستقبال
- لوحة الاتصال، دليل المؤسسة والمفضلة، السجل الشخصي، البريد الصوتي، الحساب والصوت.
- صفحتا incoming وreception مع كل النماذج التابعة.
- ملاحظات، شكاوى (قسم، أولوية، حالة)، متابعة مستقبلية (بتوقيت بغداد)، ملخص ما بعد المكالمة.
- عدم فقدان المسودة؛ لا بدء استقبال جديد قبل إنهاء الملخص.
- الميكروفون والإشعارات بطلب إذن فقط؛ في غياب اتصال حقيقي عرض "غير متصل" ووضع محاكاة صريح.

### 2.7 CRM (باشتراك مستقل)
- إدارة الاشتراك للسوبر أدمن (فترة، حدود مستخدمين/عملاء، عملة، قيمة اختيارية، طلبات تفعيل، سجل).
- المؤسسة: عملاء، ملفاتهم، ملاحظات، تواصل، فرص ومراحل، مهام، شكاوى، تقارير.
- التحقق من التفعيل والفترة والحدود خادمياً عند كل عملية.
- التعليق والانتهاء يحجبان العمل دون مسح البيانات.

### 2.8 VODNOX FORMS (باشتراك مستقل)
- إدارة الباقات والفترات والحالات وحدود النماذج والردود والمستخدمين وطلبات التفعيل.
- منشئ النماذج بكل أنواع الحقول الـ11، ترتيب، نسخ، شروط ظهور، تسمية، مساعدة، إلزام، حدود، هوية، نشر، رسائل شكر.
- روابط عامة بـ Permanent opaque tokens من الخادم (لا snapshot في fragment).
- الردود تحفظ مركزياً؛ تحقق خادمي من الاشتراك والنشر والمهلة والحصة والحقول والشروط عند الإرسال.
- transaction لحماية الحصة المتزامنة.
- إصدار schema عند النشر لحماية الردود القديمة عند تعديل الحقول.
- تصدير CSV آمن (حماية الصيغ، UTF-8 للعربية).

### 2.9 إعدادات الاتصالات وIVR العادي (مضمّنان تلقائياً)
- جداول بأيام وأوقات بغداد، لموظف واحد أو اثنين، متزامن أو متتابع بترتيب.
- مدة رنين 5–120 ثانية؛ لكل موظف في التتابع.
- منع تكرار نفس الموظف، منع تداخل الجداول المفعّلة، منع بداية=نهاية.
- دعم منتصف الليل ونهاية الأسبوع ونهاية الفترة exclusive.
- مسارات عدم الرد والافتراضي وخارج الدوام: بريد صوتي، رسالة ثم إنهاء، إنهاء، موظف بديل (مرة واحدة 20 ثانية ثم بريد صوتي، لا دوران).
- IVR: رسالتي ترحيب AR/EN، أزرار 0–9 فريدة ووجهاتها، timeout 3–30 ثانية، 0–3 إعادة محاولات، مساري نفاد المحاولات.
- أداة اختبار المسار كمحاكاة فقط.

### 2.10 المجيب الآلي الذكي (قريباً)
- اشتراك مستقل inactive/active/supervised من السوبر أدمن.
- عند active يظهر قسم "قريباً" لمسؤول المؤسسة؛ عند التعليق يختفي ويمنع الوصول المباشر خادمياً.
- لا AI، لا مفاتيح، لا محادثة.

### 2.11 تكامل سيرفر الاتصالات
- `TelephonyGateway` interface + محاكي + HTTP adapter قابل للإعداد.
- أوامر Provisioning في Jobs مع retry/backoff وidempotency.
- Webhooks موقعة (timestamp + nonce + replay prevention)، معرف حدث فريد.
- بيانات الخادم في env/encrypted storage فقط.
- لا تشغيل فعلي حتى توفر البيانات.

## 3. المتطلبات غير الوظيفية

- **التقنيات**: Laravel 12، PHP 8.2، MySQL (utf8mb4)، Blade Views (دون Components)، HTML/CSS/Bootstrap 5/Vanilla JS، Laravel UI للمصادقة.
- **ممنوع**: React, Vue, Inertia, Livewire, Alpine, Tailwind, jQuery, Breeze, Jetstream.
- **اللغات**: العربية افتراضية، إنجليزية بديلة، RTL/LTR، فاتح/مظلم.
- **الأمان**: XSS escaping، CSRF، FormRequests، Policies، Rate limiting، تخزين الملفات الخاصة خارج public، audit بدون أسرار.
- **الوقت**: UTC للتخزين، Asia/Baghdad للعرض والجداول والأوقات المحلية.
- **الاستقلالية**: التطبيق يعمل بعد حذف مجلد `VODNOX-Full-Handoff` تماماً.
- **لا npm في الإنتاج**: الأصول المبنية مُسلّمة في `public/`.

---

## 4. القيود والافتراضات

- قاعدة البيانات الحالية (vodnox) لا تُمسح؛ تستخدم migrations إضافية غير مدمرة.
- لا بيانات اتصال فعلية لـ Asterisk/SMTP/دفع متاحة؛ تُنفذ الحدود والمحاكاة فقط.
- تصاميم الواجهات في المرفقات هي المصدر النهائي للتصميم.
- Bootstrap 5 هو مكتبة الواجهة الوحيدة.
- الديمو Seeder منفصل واختياري للاختبار فقط.

## 5. معايير القبول (Acceptance Criteria)

### قواعد (Rules)
- **R1**: جميع صفحات ROUTE_MAP منفذة كـ Blade views مع المسارات المقابلة.
- **R2**: المصادقة تعمل بـ username/password مع CSRF وrate limiting وخروج POST.
- **R3**: تغيير `organization_id` أو record ID في URL/body لا يكشف بيانات Tenant آخر (IDOR ممنوع).
- **R4**: إعدادات الاتصالات وIVR متاحة تلقائياً للمؤسسة المفعّلة دون اشتراك إضافة.
- **R5**: Smart IVR مخفي وممنوع الوصول المباشر ما لم يكن الاشتراك active.
- **R6**: إرسالان متزامنان عند الرد الأخير للنموذج لا يتجاوزان quota.
- **R7**: جدول الأحد 09:00–17:00 يطابق 09:00 ولا يطابق 17:00 (نهاية حصرية).
- **R8**: جدول السبت 22:00–الأحد 02:00 يطابق الأحد 01:00 ولا يطابق 02:00 (منتصف الليل).
- **R9**: رفض وقت بداية=نهاية، يوم فارغ، نفس الموظف مرتين، موظف Tenant آخر أو غير فعّال.
- **R10**: الفاتورة لا تتحول paid تلقائياً عند رفع إثبات الدفع.
- **R11**: التطبيق يعمل بشكل كامل بعد حذف مجلد `VODNOX-Full-Handoff`.
- **R12**: لا توجد أسرار أو tokens في Git أو `.env.example`.
- **R13**: جميع طلبات `/api/*` ترجع JSON عند الخطأ (لا HTML ولا redirect).
- **R14**: `composer.lock` و`.env.example` وmigrations وREADME و ATTACHMENT_INDEPENDENCE_REPORT.md موجودة.
- **R15**: route:list يعمل و migrations تنفذ على قاعدة اختبار دون أخطاء.

### معايير تقييم (Rubrics)
- **RU1 (تصميم وطابور الواجهة 0-2)**: 2=مطابق للتصميم المرفق بالكامل، 1=مطابق جزئياً، 0=اختلاف كبير.
- **RU2 (جودة الكود والبنية 0-2)**: 2=Controllers رفيعة، Services وPolicies وFormRequests منفصلة، 1=بنية مقبولة، 0=منطق داخل Blade أو Controllers ضخمة.
- **RU3 (الاستجابة والأداء 0-2)**: 2=استجابة سريعة (<2s للصفحات)، 1=مقبول، 0=بطء ملحوظ.
- **RU4 (الأمان 0-2)**: 2=كل الحمايات مطبقة ومختبرة، 1=بعض الحمايات، 0=ثغرات واضحة.
